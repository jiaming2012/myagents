## 2. Weekly cycle (after the catch-up)

```
cd ~/projects/yumyums/accounting/xero && task toast:export -- --from <last> --to <today>   # new Toast sales days
cd ~/projects/myagents/finance-tools
task zoho:toast-dump            # refresh .toast_preview_2026.json
task zoho:recon                 # dry run: pairing table, plan, unmatched merchants
task zoho:recon:apply           # categorize / match / Toast journals; stops cleanly at the API cap
task zoho:reconcile -- --apply  # month-end records for any newly complete month
```
Unmatched merchants are printed with a suggested `merchants.yaml` line; add them and
re-run apply. New patterns also need `task zoho:rules -- --apply` so future feed lines
auto-categorize (rules fire at feed import, i.e. zero API calls).

## 3. How the script decides (per Mercury transaction)

1. **Pair** each Mercury posted txn with one uncategorized Zoho line: exact Eastern
   date, |amount|, direction; then ±1/±2 days; tie-break on the merchant name inside
   Zoho's `description` (which ends in `Merchant name: <Mercury counterparty>`).
2. **Classify** with `mercury_precode.classify` (skip → transfers → merchants).
3. **Internal transfer** (both accounts in Zoho): the money-out side categorizes
   `transfer_fund`; the other side's line is **matched** to that document. If the
   other side was posted in an earlier run, this side matches first and only creates
   when Zoho offers no candidate.
4. **Spend** → `categorize/expenses`; **refund** → `expense_refund`; **owner draw**
   (code 3200) → `owner_drawings` / `owner_contribution`.
5. **Toast payout** → journal (debit bank for the net payout; toast_xero's positive
   lines become credits, negatives debits) then match the feed line to the journal.
6. **No-feed account** (`statement_import: true`) → its Mercury history is pushed in
   once with `POST /bankstatements`, then steps 1–5 apply.
7. Every document carries `reference_number mercury:<id>`; the checkpoint records it.

## 4. Month-end reconciliation records (`--reconcile`)

- Zoho reconciles by **its own document dates**. Opening of a period = sum of
  reconciled documents dated before it; every unreconciled document dated inside the
  period is selected; closing = opening + selected. The first period includes the
  opening-balance document dated 2025-12-31.
- Mercury's month-end is printed beside Zoho's. They differ only by **straddlers**:
  Mercury postings late on the last day (Eastern) that the feed dates on the 1st. Each
  straddler reverses the next month; the script lists them under the table.
- `transactions_to_be_reconciled` must be a **plain list of id strings**.
- A saved draft blocks new records (`19009`); `DELETE …/reconciliations/{id}` undoes
  the last one. Reconciled documents and the opening-balance record become immutable
  (`19007`, "This transaction has been reconciled").

## 5. Repairs

| symptom | fix |
|---|---|
| A line was categorized wrongly | `POST /banktransactions/{imported_transaction_id}/uncategorize` with the **statement-line id** (`imported_transaction_id` on the categorized row; the document id returns 108005). The document is deleted and the line returns to uncategorized. Remove the mercury id from the checkpoint, fix `merchants.yaml`, re-run apply |
| A transfer got posted twice | `python3 zoho_books_recon.py --undo-created-transfers <zoho account id>` re-runs match-first for every transfer created from that account's side |
| Statement import went in reversed | `GET /bankaccounts/{id}/statement/lastimported` → `DELETE /bankaccounts/{id}/statement/{statement_id}`; clear `_imported:<id>` from the checkpoint. Import convention: **credit = money in** (opposite of the listing) |
| Opening balance missing for a new account | the org record is reconciled and immutable; the script posts a journal (bank ↔ Opening Balance Offset, reference `opening:<id>`) instead |
| A rule points at the wrong account | rules with auto-categorize cannot be deleted (108100); `PUT /bankaccounts/rules/{id}` with the full body |
| Feed lines "missing" | they only list under `filter_by=Status.Uncategorized`; `Status.All` returns none |
| A BoA transfer was posted twice (both accounts show a `manually_added` + a `categorized` transfer_fund for the same date/amount) | happens when a run stops between creating one side and matching the other (`--limit`, API cap): the next run no longer sees the posted side and must match first. `--feed-only` now matches first on one-sided groups; to repair an existing duplicate: `POST /banktransactions/{line id}/uncategorize` on the second side's line, delete its `boa:<line id>` checkpoint key, re-run `task zoho:boa:apply` (verified 2026-10-17) |
| Everything 429 | code 44 = per-minute (script backs off); **code 45 = 1,000 calls/day for this org** (script stops; resume next day — the checkpoint makes re-runs free of duplicates) |

## 6. API budget (1,000 calls/day on this org)

| operation | calls |
|---|---|
| spend / refund / owner draw | 1 |
| internal transfer (both sides) | 3 (create, match lookup, match) |
| Toast payout | 3 (journal, match lookup, match) — plus 1 lookup on re-runs |
| statement import of N lines | 1 |
| bank rule | 1 (and 0 forever after: rules categorize at feed import) |
| month-end record | 1 |
| run overhead | ~15 (chart, banks, feed listing per account, Mercury is free) |

Zoho has no bulk categorize/match endpoint; the levers are rules (free), the
statement import (one call), and not re-running what the checkpoint already covers.
